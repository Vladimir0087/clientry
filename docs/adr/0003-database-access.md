# 0003 — Database access

Status: accepted
Date: 2026-10-01

## Context

CRM data is relational: workspaces own clients, deals reference clients, stages and users,
and pipeline moves must update a deal and its activity in one transaction. Production runs on
Neon's free tier, which suspends compute when idle, so the API must start and keep serving while
the database is asleep or down.

## Decision

- **PostgreSQL** (Neon in production, `postgres:18` in Compose and testcontainers).
- **Prisma 7** with the `prisma-client` generator, output in `src/infra/prisma/generated`
  (gitignored, generated by a cached Turborepo task), and the **`@prisma/adapter-pg`** driver
  adapter. The pg pool connects on first query with a 5-second connect timeout, so startup
  never waits for the database and readiness reports it as `down`.
- **Prisma Migrate**: SQL migrations in `prisma/migrations`, `migrate deploy` before the server
  starts, and an integration harness that deploys the chain on an empty database and fails on
  drift between the migrations and `schema.prisma`.
- `PrismaService` is the only place the client is constructed; query logs go to pino at
  `debug` for N+1 checks.

## Alternatives

- **MongoDB.** The data has joins and transactional invariants that a document store pushes
  into application code, and Postgres is what backend job posts ask for. Rejected.
- **TypeORM.** Decorator entities fit Nest, but its types are looser (relations and partial
  selects are not reflected in result types) and its migration generator is less reliable.
  Rejected.
- **Drizzle.** Lighter and SQL-shaped, but migrations and the client are younger, and Prisma's
  generated types and Migrate workflow are more widely known. Rejected for now.
- **Prisma Accelerate instead of a driver adapter.** Prisma 7's client needs one of the two.
  Accelerate puts a hosted pool and cache in front of the database: one more service and network
  hop for a single API instance, with pool timeouts out of our hands. Rejected; pg keeps them in
  the code.

## Consequences

- Repositories get fully typed queries; services are tested against repository mocks.
- `prisma generate` must run before typecheck, lint, test and build; Turborepo handles it.
- The `latest` tag of `prisma` points at an 8.0 release candidate, so `prisma`,
  `@prisma/client` and `@prisma/adapter-pg` are pinned together to the same 7.x release and
  upgraded together.
- Applied migrations are never edited; risky changes go through two migrations.
